## アプリへ組み込む時の提案

### 入口

- **ものがたりっちの案件画面に「相談」を置く**
  - 開いている案件の台本・香盤表・取材メモ・NG事項を、「案件資料」として自動で添える
  - 評価では案件資料を毎回渡した前提で測っている。案件を選ばずに聞ける入口だと、案件資料の無い問が増える
  - 案件を選んでいない時は、マニュアル・構成のルール・公開前チェック・qa.md だけで答える。案件に依存する問は「案件を開いてから聞いてください」と返す
- **呼び出し**：Worker（mg-share）から Claude API を呼ぶ
  - system に `agent/PROMPT.md` と資料を入れる。資料は固定なので、プロンプトキャッシュを効かせる
  - 案件資料と質問は user に入れる
  - 評価と同じく、**1問ずつ独立して**答えさせる（会話の続きにしない）。前の問の答えを前提にした答え過ぎを防ぐため
- **出力の扱い**：出力形式（`判定:` `回答:` `出典:` `AKへの理由:` `資料にある手順:` `AKに渡す質問文:`）はそのまま機械で読める
  - 「判定: AKへ」の時は、「AKに渡す質問文」を通知に使う
  - 形式が崩れていたら（判定の行が無い等）、答えを出さずにAKへ回す側に倒す

### ログの形

D1 に1問1行で残す（例：`agent_log`）。

| 列 | 中身 |
|---|---|
| id / created_at | 一意のID・日時 |
| case_id | 案件ID（無ければ空） |
| asker | 質問者（ログインのメール） |
| question | 質問の原文 |
| verdict | 回答 / AKへ |
| category | AKへの6分類（お金・スケジュール・クライアント対応・構成変更・センシティブ・資料に無い）。回答なら空 |
| sources | 出典の配列 |
| answer | エージェントの出力の全文 |
| ak_question | AKに渡す質問文 |
| prompt_version | 答えた時のプロンプトの版（あとで版ごとの比較ができる） |
| status | open / answered / closed |
| ak_answer / answered_at | AKの回答 |
| qa_scope | qa.md に追記した時の適用範囲（この案件限定／このチャンネル共通／全案件共通）。追記しなければ空 |
| feedback | 質問者の「役に立った／違った」（任意） |

このログから、マニュアルの「継続判断」が出せる。
- 2週間ごとの質問数
- 直接答えた件数と、AKへ回した件数の比率

あわせて残すとよいもの：
- 「違った」の件数と、AKが答えを見て直した件数。正答率の材料になる。ただし、正答率を継続判断に足すかはAKの判断（上の穴13）

### AKへ回す時の通知先

- **ものがたりっちの通知（ベル）に、AK宛てで出す**
  - 本文：「AKに渡す質問文」＋案件名＋質問者
  - 開くと、エージェントの出力全文（理由欄・手順欄）が見える
  - 急ぎ（撮影日が近い等）は、AKのメールにも送る。Slack を使うなら DM でもよい
- **AKが答えたら、質問者に通知する**
  - あわせて、qa.md に追記する下書きを出す（質問の要約・AKの回答・適用範囲を選ぶ欄）
  - qa.md への追記は、AKが適用範囲を選んで確定した時だけにする（ナレッジの変更はAKの承認が要る、という今の決まりのまま）
- **同じ種類の質問が溜まったら知らせる**：同じ category で答えの無い「AKへ」が増えたら、まとめてAKに知らせる
  - この7日間の穴で多かったもの：★の扱い・センシティブの基準・担当とのやり取り
  - これらは1回答えれば、全案件共通で効く

### 組み込み後も評価を続ける

- 7日間の140問と想定（`runs/*.md` の「出題と想定」）は、そのまま回帰テストに使える
- プロンプトや資料を変えた時は、少なくとも前回失敗した問と★の問を流して、振り分けが崩れていないかを見る
- 実際の質問ログから、AKの回答と食い違った問を拾って、出題に足す
